# Proposed Evaluation Plan

## Graph-Based Verification of LLM-Generated DeFi Intents

Status: proposal for supervisor feedback, not completed evaluation results.

### 1. Objective and scope

Evaluate whether natural-language DeFi requests are correctly converted into
structured intents and whether graph-based relationship verification correctly
accepts or rejects them. Evaluate intent generation and verification separately
so that a correct graph decision cannot conceal an incorrectly understood request.

The primary evaluation covers Uniswap V3 and Aave V3 requests on Ethereum
Sepolia. It stops at the verification result: no transactions are signed or
broadcast. Approval means consistency with the required relationships and trust
policy in the recorded graph snapshot, not guaranteed transaction success.
Balances, liquidity and execution are outside the primary graph experiment.
Section 9 adds a separate wallet-policy and execution-readiness evaluation;
live reserve restrictions remain outside implemented lending execution.
Prompt-injection prevention is explicitly outside scope; ordinary
invalid requests do not constitute a prompt-injection security evaluation.

General informational questions such as “What is Aave?” may be included as
out-of-scope inputs, but answering them is not an evaluated capability.

### 2. Research questions

1. How accurately does the LLM extract action, protocol, assets, amount and network?
2. Does relationship verification accept valid combinations and reject invalid
   combinations, including cases where the individual entities exist?
3. How often does the complete pipeline produce both the correct intent and the
   correct disposition of the original request?
4. What are the verification and end-to-end latency distributions?
5. Can the result be traced to graph evidence or a meaningful rejection reason?

### 3. Dataset and reference labels

Create an initial researcher-authored dataset of 120 natural-language requests:

| Category | Requests | Purpose |
|---|---:|---|
| Valid swap requests | 20 | Supported token pairs, direction and amount extraction |
| Valid lending requests | 20 | Supply, withdraw, borrow and repay where supported by the snapshot |
| Invalid entity combinations | 20 | Known entities with an unsupported protocol/action or resource combination |
| Unknown or unsupported entities | 20 | Unknown protocols/assets and explicitly unsupported networks |
| Incomplete or ambiguous requests | 20 | Missing required fields, conflicting instructions or multiple possible intents |
| Invalid parameters or out-of-scope requests | 20 | Nonpositive amounts, same-token swaps and nontransactional questions |

These counts are a manageable starting design, not a statistical power claim.
Select valid cases only after checking the recorded graph and source evidence.
Include varied wording and token amounts; do not describe synthetic requests as
real user data. If LLM-assisted authoring is used, disclose it and independently
review all labels.

Reserve 30 requests for development and 90 for the final held-out test, aiming
for five development and fifteen test requests per category. Split by underlying
scenario/paraphrase family to prevent near-duplicate leakage. Freeze the test set
before final prompt tuning; do not edit labels to match observed model outputs.

Record for each case:

- Case ID, prompt, category and scenario family.
- Expected structured fields, or the ambiguity/missing information that prevents
  a complete intent; record any explicitly allowed normalisation.
- Expected disposition: APPROVE or DO NOT APPROVE, and the expected stage/reason.
- Source references, relevant snapshot relationships and a short justification.

A rejected intent can still be correctly extracted: for example, an unknown
protocol should not be silently replaced with a recognised protocol. Decide and
document missing-field/default rules in advance. For this experiment, require a
positive amount and an explicit network for an approvable transaction request;
allow null token_out for single-asset lending actions. Ambiguous requests may be
rejected with an explanation; do not claim a clarification dialogue exists unless
implemented.

Reference labels should be manually checked against protocol evidence and the
declared application policy, not generated by the verifier being tested. Request
an independent review of at least 20% of cases, covering all categories, if a
second reviewer is available. Record disagreements and resolutions.

### 4. Experimental procedure

**A. Intent generation and validation**

Send each natural-language prompt to the actual LLM parser. Store its raw output,
parsed intent, validation result and latency. Compare extracted fields with the
reference labels. Do not supply reference intents to the LLM.

**B. Isolated graph verification**

For cases with well-defined, schema-valid reference intents, bypass the LLM and
send those intents directly to the verifier. This isolates graph-verification
errors from extraction errors. Test malformed or incomplete intents separately
at the validation boundary rather than forcing them through the graph verifier.

**C. End-to-end evaluation**

Run prompt -> LLM -> deterministic validation -> graph verification -> result.
Use the actual generated intent, without manually correcting it. Compare the
outcome to the original request and reference labels. An approved result counts
as end-to-end correct only if all required intent fields are also correct.

Run every held-out prompt three times with the same recorded configuration,
retaining all results. Report the first run as the primary per-prompt result and
the repetitions as a consistency analysis; do not treat repeats as independent
new requests or select the best run.

**D. Relationship-specific checks**

In a separate test database, create controlled variants of valid examples by
removing one required edge, making a required membership inactive, or connecting
a resource to the wrong deployment. Check that approval becomes rejection.
Preserve the production/demo database. Use an entity-existence-only baseline in
this isolated test to demonstrate whether checking relationships adds value over
merely recognising the protocol and asset names. Report this as a diagnostic
comparison, not as a comprehensive comparison with other research systems.

### 5. Metrics

| Aspect | Metric |
|---|---|
| Output format | Valid JSON rate and schema-valid intent rate |
| Intent extraction | Accuracy per field and all-required-fields exact-match rate after declared normalisation |
| Graph decisions | Confusion matrix and accuracy on schema-valid reference intents |
| Incorrect approvals | False approvals / cases that should not be approved; report counts and denominator |
| Incorrect rejections | False rejections / cases that should be approved; report counts and denominator |
| End-to-end performance | Correct intent plus correct disposition / all held-out requests |
| Robustness | Agreement across three runs and across paraphrases |
| Traceability | Approved results with expected address/function evidence; rejected results with correct, useful reasons |
| Performance | Median, p95 and maximum latency; timeout/error counts |

Report metrics by category as well as overall. Keep parsing errors, validation
rejections, graph rejections and infrastructure failures separate. Infrastructure
failures must never count as successful semantic rejections. Include uncertainty
intervals for primary proportions where practical; zero observed false approvals
is not proof of safety outside the tested cases.

### 6. Latency and the proposed two-second requirement

Define verification latency as elapsed wall-clock time from entry to the graph
verifier until its decision is available, including graph-query time but excluding
LLM generation and transaction execution. Measure LLM, deterministic validation
and complete pipeline times separately with a monotonic high-resolution timer.

Proposed interpretation for supervisor agreement: p95 graph-verification latency
at or below 2,000 ms under the documented local, single-request conditions. This
is a project engineering target, not a universal DeFi standard or an already
demonstrated result. If R6 requires every request to finish within two seconds,
report exceedances and maximum latency rather than quietly substituting p95.

Report cold-start and warmed measurements separately. Log hardware, database and
graph size, software versions, model identifier/settings, concurrency and network
conditions. Exclude graph population from request latency and state this boundary.

### 7. Preparation required before final evaluation

The existing parser produces JSON, but the current API does not yet provide a
complete deterministic validator for the generated intent. It also passes a
fixed Sepolia chain ID to the verifier. Before final testing:

1. Implement explicit schema, amount, action-specific field and network checks;
   reject mismatches instead of silently substituting the supported network.
2. Define output states and map the existing APPROVED/BLOCKED labels consistently;
   preserve separate parse, validation and infrastructure error categories.
3. Build a verification-only console runner that records each stage and never
   imports or invokes transaction execution.
4. Freeze a graph snapshot and its provenance, model/prompt configuration and
   dataset split. Record manually curated function/action mappings as such.
5. Add auditable evidence/reason logging. Current generic “No trusted path”
   messages must not be presented as identifying a specific failed relationship.
6. Map the final experiment IDs to the exact thesis requirements once their
   wording is fixed; do not claim coverage of untested execution requirements.

The current graph models structural support. In particular, its reserve action
mappings do not establish live paused/frozen status. Freshness enforcement should
not be claimed unless a defined validity policy is implemented and tested.

### 8. Professor demonstration and deliverables

Before the full experiment, demonstrate six development-set requests: two valid,
one invalid combination, one unknown entity, one wrong-network request and one
incomplete request. Print the prompt, LLM-generated intent, validation result,
graph decision, evidence/reason and per-stage timing. Clearly distinguish this
demonstration from held-out evaluation.

Deliver the labelled dataset, verification-only runner, frozen configuration and
snapshot description, per-case JSON/CSV logs, summary tables, latency plots and
an error analysis. No numerical performance claim is made until experiments run.

Supervisor decisions requested: confirm the primary Sepolia verification scope,
the supplementary wallet/preflight scope below, dataset size, missing-field
policy and interpretation of the two-second target. Actual submission requires
a separately approved testnet experiment.

### 9. Supplementary wallet-policy and execution-readiness evaluation

#### 9.1 Distinguish the decisions

A graph approval is not execution permission and is not transaction success.
Record separate outcomes for intent validation, graph verification, wallet
policy, preflight, submission and receipt. A later-stage failure must not change
an earlier correct graph approval into a graph-verification error.

For example, the same correctly parsed USDC-to-WETH swap can have a valid graph
path but be blocked because a required destination is not permitted, because the
smart wallet lacks tokens, or because no usable quote can be obtained.

Use a state-conditioned scenario record, not just a prompt:

`prompt + reference intent + graph snapshot + wallet policy + account state +
RPC/quote conditions -> expected outcome at each stage`

Record stages not reached as NOT_RUN, rather than PASS. Test each negative case
with all earlier conditions satisfied so that the intended failure is reached.
Pair each negative case with a passing control where practical. Mocked results
must be labelled as mocked; passing a mocked policy test does not establish
on-chain enforcement.

#### 9.2 Current implementation boundaries

The following findings are based on inspection of `wallet/wallet.mjs`,
`wallet/erc4337.py` and `api/app.py`:

- The whitelist is a local JSON list of destination contract addresses. Swap
  preparation checks the router and input-token contract. This is not an
  allowlist of user accounts or an on-chain restricted session-key policy.
- The wallet is configured with an ECDSA sudo validator. Documentation that
  calls the local whitelist an ERC-4337-enforced session-key restriction should
  not be used as evidence of that property.
- The normal execute endpoint automatically adds graph-derived destinations to
  the whitelist. Test missing-whitelist cases at the policy/preflight boundary
  with isolated state. Do not claim this normal path demonstrates independent
  user permission; an independent policy would need explicit design and enforcement.
- Expired local whitelist data is reported explicitly as `POLICY_EXPIRED` by
  policy checks. Adding a newly graph-verified destination renews the local
  policy window; this remains a local control rather than on-chain enforcement.
- The native-value limit is per call, and swaps call the policy check with zero
  native value. It does not implement a cumulative ERC-20 spending budget.
- The connected wallet address is not proof of signer authority: the backend
  account is derived from the configured private key. User-to-signer binding
  needs separate design/testing before claiming user-account authorisation.
- Swap preparation validates routes, obtains quotes, checks the smart wallet's
  token balance and builds allowance/transaction calls. Insufficient allowance
  normally causes an approval call to be added, not an automatic rejection.
- The execute endpoint consumes a short-lived, one-time capability for a
  server-held approved structured operation. It rechecks that operation against
  current graph authority without reparsing browser-supplied natural language.
- Graph-approved Aave `supply`, `withdraw`, `borrow`, and `repay` operations can
  be submitted through the same ERC-4337 wallet boundary as approved swaps.

#### 9.3 Scenario coverage matrix

This is a scoped coverage matrix, not a claim to exhaust every blockchain failure.
Reason codes below are proposed stable evaluation labels, not existing API fields.
“Planned” denotes a required check/test whose enforcement is not established by
the current implementation. Isolated fixtures must not change the demo database,
real whitelist or real account balances.

| ID | Condition, with earlier stages satisfied | Expected stage/outcome | Proposed reason or evidence | Status / test approach |
|---|---|---|---|---|
| I01 | Complete, valid natural-language request | Intent validation PASS | All required fields correct | Add deterministic validator; actual LLM run |
| I02 | Malformed LLM JSON or wrong field types | Intent validation BLOCKED | INVALID_INTENT_FORMAT | Parser/validator fixture; separate from natural-language set |
| I03 | Missing amount, network or required asset | Intent validation BLOCKED | MISSING_REQUIRED_FIELD | Planned explicit policy |
| I04 | Ambiguous or conflicting request | Intent validation BLOCKED or clarification | AMBIGUOUS_INTENT | No silent guessing; clarification only if implemented |
| I05 | Zero/negative amount or excessive token precision | Validation/preflight BLOCKED | INVALID_AMOUNT / INVALID_PRECISION | Test decimal handling and rounding explicitly |
| I06 | Explicit unsupported network | Intent validation BLOCKED | UNSUPPORTED_NETWORK | Add deterministic network enforcement |
| G01 | All mandatory graph relationships present | Graph APPROVED | Matched deployment, contract, function and resource | Existing verifier |
| G02 | Unknown protocol or asset | Graph BLOCKED | NO_TRUSTED_PATH | Existing generic reason; enrich evidence if needed |
| G03 | Known entities but wrong action/deployment relationship | Graph BLOCKED | RELATIONSHIP_MISMATCH | Isolated reference-intent tests |
| G04 | Required edge missing or membership inactive | Graph BLOCKED | MISSING_OR_INACTIVE_RELATIONSHIP | Isolated graph variants |
| G05 | Swap pool/asset discovered but not verification-eligible | Graph BLOCKED | RESOURCE_NOT_ELIGIBLE | Existing swap trust filters |
| G06 | Same-token swap | Validation/graph BLOCKED | IDENTICAL_SWAP_ASSETS | Existing graph condition; validator check planned |
| G07 | Evidence beyond a declared freshness limit | Graph BLOCKED | STALE_EVIDENCE | Planned: freshness enforcement not currently established |
| G08 | Database unavailable or query timeout | Infrastructure ERROR, no handover | GRAPH_UNAVAILABLE | Fault injection; not a successful semantic rejection |
| W01 | Both required destinations allowed | Local policy PASS | Router and token addresses checked | Implemented; isolated local whitelist evaluation |
| W02 | Router or token destination missing from whitelist | Local policy BLOCKED | DESTINATION_NOT_ALLOWED | Implemented; isolated policy evaluation bypasses auto-add |
| W03 | Local whitelist expired | Local policy BLOCKED until renewed by defined policy | POLICY_EXPIRED | Implemented with explicit stable reason code |
| W04 | User/signer unauthorised or mismatched | Wallet authorisation BLOCKED | UNAUTHORISED_SIGNER | Planned binding/enforcement; not proven by local whitelist |
| W05 | Native-value limit exceeded | Local policy BLOCKED | NATIVE_VALUE_LIMIT_EXCEEDED | Implemented and evaluated; not an ERC-20 budget |
| W06 | Token spending budget exceeded | Wallet policy BLOCKED | TOKEN_BUDGET_EXCEEDED | Planned, if included in requirements |
| H01 | Approved amount, recipient, chain or target altered before execution | Handover BLOCKED | REQUEST_SCHEMA_REJECTED / APPROVAL_MISMATCH | Implemented with server-held structured operation and current-authority recheck |
| H02 | Approval expired or reused against a one-use policy | Handover BLOCKED | VERIFICATION_EXPIRED / VERIFICATION_REUSED | Implemented with atomic one-time capability claims |
| P01 | Invalid selector, signature, address or inconsistent routes | Preflight BLOCKED | INVALID_EXECUTION_DATA | Implemented; isolated JavaScript wallet fixtures |
| P02 | Graph-approved Aave structured operation is valid | Preflight PASS | EXECUTION_DATA_VALID | Implemented for supply/withdraw/borrow/repay |
| P03 | Smart wallet token balance below amount | Preflight BLOCKED | INSUFFICIENT_TOKEN_BALANCE | Implemented for swap and Aave supply; deterministic funding fixtures |
| P04 | Balance sufficient, allowance insufficient | Preflight PASS with approval call(s) | ALLOWANCE_APPROVAL_REQUIRED | Implemented for swap, Aave supply and repay |
| P05 | Balance and allowance sufficient | Preflight PASS without extra approval | PREFLIGHT_READY | Implemented; deterministic funding fixture |
| P06 | All candidate pools fail to provide a usable quote | Preflight BLOCKED, or infrastructure ERROR where identifiable | NO_USABLE_QUOTE / RPC_UNAVAILABLE | Do not assert lack of liquidity from an RPC error alone |
| P07 | Slippage configuration outside allowed bounds | Preflight BLOCKED | INVALID_EXECUTION_DATA | Implemented range check and evaluated fixture |
| P08 | Positive quote becomes zero minimum output after rounding | Preflight BLOCKED | OUTPUT_TOO_SMALL | Boundary fixture |
| P09 | One route fails but another provides a usable quote | Preflight PASS | Usable route selected | Controlled quote responses |
| P10 | Token approval or complete call batch reverts in simulation | Simulation BLOCKED | SIMULATION_REVERTED | Controlled wallet-boundary fixture; no broadcast |
| E01 | Sponsorship refused or gas funding unavailable | Submission not accepted | SPONSORSHIP_DENIED / GAS_FUNDING_UNAVAILABLE | Controlled wallet-boundary fixture |
| E02 | Nonce/signature rejected by bundler | Submission not accepted | INVALID_NONCE / INVALID_SIGNATURE | Controlled fixture; no invalid real submission |
| E03 | Timeout after submission; receipt unknown | Status UNKNOWN/PENDING | RECEIPT_UNCONFIRMED | Never report definitive rejection or retry blindly |
| E04 | Operation included but execution reverted | Execution FAILED | EXECUTION_REVERTED | Controlled receipt fixture; real receipt only in approved testnet experiment |
| E05 | Wallet boundary reports successful submission | Execution SUBMITTED | TRANSACTION_SUBMITTED | Controlled fixture; not evidence of a real confirmation |

#### 9.4 Recording reasons and evidence

Each scenario log should include scenario ID, original prompt, generated intent,
graph decision, policy outcome, preflight outcome, final status, failed stage,
stable reason code, human-readable explanation and whether submission occurred.
Record the underlying evidence for the reason. Do not infer a specific failed
relationship from an empty graph query alone. Preserve per-stage durations.

Example of the proposed console format (illustrative, not an executed result):

```text
Scenario: W02 -- valid swap, router not permitted
Intent validation: PASS
Graph verification: APPROVED
Local wallet policy: BLOCKED
Reason: DESTINATION_NOT_ALLOWED -- router absent from permitted destinations
Preflight: NOT_RUN
Submission: NOT_RUN
Transaction sent: NO
```

#### 9.5 Evaluation phases and acceptance

1. Primary evaluation: the natural-language dataset and isolated graph tests.
2. Supplementary offline evaluation: policy, route and error-handling scenarios
   using an isolated whitelist and mocked balances, quotes and service responses.
3. Optional read-only integration: real Sepolia quotes/balances and preflight,
   with no broadcast; record changing state and do not silently auto-grant policy.
4. Optional testnet execution: only after separate approval of accounts, spending
   limits and transaction count. Verify operation receipts before claiming success.

For every implemented requirement, include a passing case, a failing case and
relevant boundary cases. Track planned/unimplemented tests separately from passed
tests. Include selected combined failures to test which stage reports first, but
do not attempt every combinatorial permutation. An unavailable dependency must
fail closed before submission; uncertainty after submission requires explicit
pending/unknown status instead. Report stage-level correctness, reason accuracy
and improper progression to later stages in addition to the primary metrics.
